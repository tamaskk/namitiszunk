# Security: Na, mit iszunk?

Read before changing auth, payments, data handling, uploads, secrets or deletion. Where this file is stricter than AGENTS.md §05, this file wins. Full review checklist: task #79 (`docs/security/checklist.md`, planned).

## 01 What we protect

| Data | Examples | Sensitivity | Where stored | Retention |
| --- | --- | --- | --- | --- |
| Guest phone numbers | SMS "ready" opt-in | personal data | orders | 30 days, then deleted (Inngest retention job), Twilio's message log too (only outbound messages of our messaging service) |
| Guest email on a problem report | optional reply address (T-046) | personal data | orders (`problemReports[].email`) | 90 days, then removed (Inngest retention job, T-028) |
| Card fingerprint | Stripe `card.fingerprint`, caps guest cancels at 1 per card, venue and business day | pseudonymous personal data | payments (`cardFingerprint`, not selected by default) | 2 days, then removed (Inngest retention job) |
| Guest accounts | email, name, order history | personal data | users | until the guest deletes it on `/fiok` (`DELETE /v1/me`, immediate, T-047); inactive accounts after 2 years without a sign-in (`User.lastSignInAt`, set on every new session) or an order, by the daily 07:00 retention job; venue and platform members are skipped; each deletion is audited as `account.deleted` by the system |
| Staff | name, PIN hash, email (Manager/Owner) | personal data, credentials | staff / users | while employed at the venue |
| Orders and payments | items, amounts, Stripe ids | financial | orders | per accounting rules (confirm with the accountant) |
| Venue payout data | Stripe connected account | financial | Stripe only; we store the account id | while the venue is active |
| Audit log | refunds, fee changes, impersonation | integrity | audit | never deleted in v1 |

Card data never touches our servers: Stripe Elements / Payment Request and PaymentSheet only.

## 02 Trust boundaries

- Browser and mobile → API: untrusted. Validate with the shared Zod schema at the route handler or server action.
- Stripe webhooks: verify the signature on the raw body before parsing; handlers are idempotent (store processed event ids).
- Ably: clients get short-lived tokens from `apps/api/app/v1/realtime/token`, scoped to one venue/bar or one order.
- Third-party responses (Stripe, Twilio, Resend): untrusted input.

## 03 Authentication and authorization

- Provider: Better Auth. Session cookie httpOnly, secure, sameSite=lax, per-app names on the `.namitiszunk.hu` parent domain in production; apps/api accepts a cookie only with an allowlisted `Origin` of the app that owns it (CSRF check), the mobile app uses a Bearer token. Sign-in: Apple, Google, email link.
- HQ requires 2FA for every platform role. Staff on the bar view use a PIN on a device signed in by a Manager. A browser with a valid staff-device cookie fails closed: without an active PIN neither the Admin nor `/v1` accepts the member session left on it (`isStaffDevice`, T-051). Only a signed-in Manager or Owner can register a device (`createDeviceSession`, T-054), never from an already registered tablet; on a tablet the Admin's Better Auth routes serve only sign-in and sign-out (`staffDeviceAllowsAuthRequest`), so the manager session left on it cannot read or change the account; the device and staff cookies are httpOnly, `SameSite=Lax`, scoped to the parent domain so `/v1` sees them (so only our own apps may ever live under `namitiszunk.hu`: a third-party CNAME there would receive and could overwrite them); the name list on `/pin` shows only active PIN roles of the device's venue, and the PIN lockout counts per device.
- Guests access their order with a per-order guest token, never with a guessable order id.
- Guest account (`/v1/me/*`, T-047): only an order-app user session (cookie with the order app's `Origin`, or Bearer from the mobile app); staff and admin sessions get 401. Device orders join the account only after the guest confirms (a shared phone may hold someone else's), only with their guest token (hash match, no account yet), never by e-mail; sign-out and deletion clear the orders stored on the device. Export holds every personal field tied to the account. Deletion removes the user, sessions, logins and push tokens in one transaction, keeps the orders for the books without `userId`, and writes an `account.deleted` audit entry without personal data; a venue or platform member gets 409 `staff_account`.
- Guest links (`/o/[orderId]?t=…`, `/r/[orderId]?t=…`) carry the token once: the order app proxy moves it into an httpOnly, secure, sameSite=lax cookie named per order (30 days) and redirects to the URL without it, so the address bar, history and print never show it. Guest pages also send no Referer and are not indexed.
- The confirmation e-mail (T-044) links with the token, so the guest can open it on another device. Accepted risk: a mistyped address gives that person the guest's access to this one order (view, report, rate; no payment or refund). At most 3 such mails per order and 30 per IP per minute.
- Roles: venue roles Owner, Manager, Bartender, VIP host; platform roles Admin, Support, Finance. Every check runs on the server through `packages/core/src/auth/permissions.ts`, with venue ownership checked on every resource.
- Refunds after hand-over: Manager or Owner only. Impersonation from HQ is read-only by default and always audit-logged.
- Orders module (T-056): only Manager and Owner (`order.viewHistory`) see the order list, details and export. Guest contact is masked on the page (`k***@gmail.com`, `+36 30 *** **12`) and never in the export; export cells that start with `=`, `+`, `-` or `@` are prefixed with `'` so a bar name cannot run as a formula.
- Staff module (T-057): staff PINs are exactly 4 digits for new members, argon2id-hashed, unique per venue (checked against every hash, disabled members included); a "PIN taken" answer tells a manager a PIN exists, the per-device PIN attempt limit still guards sign-in, and PIN writes are limited to 10 a minute per person and serialised per venue. The last active Owner cannot be disabled. A Manager manages only bartenders and VIP hosts (`staff.invite` with the target role), nobody disables themselves. A staff device is valid only while its `StaffDevice` record exists and is not revoked: sign-in, every staff request and the PIN screen check it; a revoked tablet can only forget itself, and its device cookie goes only after the member session left on it is gone. Known gap: an Ably token already issued lives up to 1 hour, so a disabled member or revoked device can still read the live channel until it expires (system-wide, not only Staff). Invite links come from the Admin's own `BETTER_AUTH_URL`, are accepted with a POST by the signed-in, verified address only (not on a staff device, not before the 2FA code), both sending and joining are in the audit log, and the sign-in return path accepts only an invite token's shape.
- Payouts (T-059): Owner only (`payout.manage`) on the page, every server action and the export. `getPayoutAccount` checks the Owner and reads the account id from our database; `fetchPayoutOverview` only accepts its result, and the Admin caches that per venue for 5 minutes behind the same check. Stripe-calling actions are rate limited (onboarding, Express Dashboard and schedule 10 a minute per person and venue, refresh 6 a minute per venue, export 3 a minute per venue), onboarding and Express Dashboard links are written to the audit log without the URL, and the export refuses a non-forint transaction instead of labelling it as forints. Export cells are neutralised like the Orders export.
- Payouts 2FA step-up (T-059): the Express Dashboard link and the payout schedule change need a session confirmed with TOTP or a backup code (`Actor.twoFactorVerified`, checked in `packages/core/src/payments/connect.ts`; otherwise 403 `two_factor_setup_required`), because the Express Dashboard can change the payout bank account. The Admin profile (`/profile`) turns 2FA on (Better Auth `two-factor/enable`, confirmed by one code; the backup codes are shown once). Known gap: there is no password to confirm the setup with (`allowPasswordless`), so a stolen session of an Owner who has not turned 2FA on yet could turn it on itself; once it is on, an unverified session can neither change the factor nor reach these actions. Owners turn it on at onboarding (pilot checklist).
- Promotions (T-060): only the Owner (`venue.editSettings`) creates, stops or restarts codes, each audit-logged; a new code needs 6 to 32 characters. The client sends only the code (`promoCodeSchema`): the discount is computed on the server from the stored rule, and the quote and the order use the same check. A guest learns only invalid (unknown, not started or stopped), expired, below minimum or used up; the last three confirm that a guessed code exists, which is accepted, since the guess had to be right first. A use is taken only when the order is paid (`takePromoUse` in `transition()`), so unpaid orders hold nothing and nobody can block a code with orders they never pay; the guest's own cancel of a paid, unaccepted order (fully refunded) gives it back. Guests paying at the same moment for the last use can overshoot `maxUses` by a few (accepted: their discount is already in the price they paid); the checkout refuses a used-up code. Guessing (`checkPromo`): a code is accepted only with the checkout's `deviceId`, a random per-browser UUID in localStorage renewed daily (`apps/order/lib/device-id.ts`), because a club crowd shares one wifi or carrier-NAT address. 10 unknown codes per device and 50 per IP in 10 minutes, then 429 `rate_limited` for any code; a valid code, or a real one refused for the cart or its period, is taken back, and a refused attempt counts nowhere. The device id is client-chosen, so the per-IP bucket is the backstop; it keys IPv6 on its /64 and every unparseable address on one shared key (`ipPrefixKey`; on Vercel x-forwarded-for is always a real address). There is deliberately no venue-wide bucket: anyone with many addresses could fill it and switch every code off, so a code's length is the defence against a distributed guess. The device id ties to no person, is stored nowhere but in short-lived rate-limit counters and is kept only for abuse prevention (strictly necessary storage); the privacy notice should still name it (T-003).
- Reports (T-061): the daily report (`report.viewDaily`) is for the Manager and the Owner, one business day at a time; a range of days, the period report and the bartender report need `report.viewAll` (Owner, HQ support, admin and finance), checked in the proxy, the page and the service, and the export refuses a Manager's multi-day daily export with 403. Reports carry no guest contact (no phone, no e-mail). The bartender report is staff performance data (display name, orders per hour, active time, tips credited to whoever marked Ready, informational only), so it stays Owner and HQ only. Exports neutralise cells that start with `= + - @`, tab or CR (`writeTableFile`), are rate limited (10 per minute per actor) and sent `no-store`. The QR source of an order (`Order.qrCodeId`) is what the guest's checkout sends, kept only when it is a code of the same venue: informational, never used for money. The weekly report e-mail (T-062) goes only to the member's own account address, and each member switches only their own (`VenueMember.weeklyReport`). It carries a week's totals and top products, no guest or staff names. A Manager who switches it on gets week totals too (decision 2026-11-14: accepted, since they can add up the daily reports they may open), but their button opens the daily report, not the Owner-only period view. The job's steps return user ids only, so Inngest's run history keeps no address or figures; each mail is built at send time and sent with a Resend idempotency key per venue, week and recipient, so a retried or re-run job does not mail twice within 24 hours.
- Refund status gate (`refundOrder`, read inside the transaction): staff refund only Picked up or Expired orders; a Cancelled order that was paid after the timeout only HQ Support or Admin with the write confirmation, or the system (automatic late-payment refund). The system also refunds Rejected and Expired orders. Anything else is 409 `refund_not_allowed_in_status`. A Manager's limit applies to the sum of the Manager refunds on the order (pending and succeeded), not to each refund.
- Refund outcome: only a definitive Stripe rejection (4xx other than 429) marks a Refund failed. A timeout, network error or 5xx leaves it pending (it counts as refunded, so nothing can be refunded twice) and it is resent with the same idempotency key (the Refund id) by a retry with the same Idempotency-Key (the Refund stores its hash as `requestKey`) or by the system refund job, within Stripe's 24-hour key window. Refund webhooks act on the refund as Stripe returns it now, not on the event snapshot; a Stripe refund without our `refundId` (made in the Dashboard) is reported.
- A PaymentIntent counts as paid only when amount, currency, application fee and connected account all match the Payment.
- Rate limits: sign-in, email link / OTP, PIN entry, payment intent creation, demo form.
- Better Auth hardening (packages/auth): a session is refused outside the app that created it (cookie or Bearer); a session that skipped TOTP may only verify, read itself or sign out; TOTP checks are limited per user (5 per 5 minutes, then a 15 minute lock) on top of the IP limit; e-mail links are limited per address and stored hashed; `/list-sessions` is disabled (it returns session tokens); Bearer tokens must be signed. PIN attempts are counted before the check, PINs unlock only Bartender and VIP host, and an unknown member costs the same argon2 check.

## 04 Secrets

- Stored in: Vercel env (production, preview) and `.env.local` (development). Never in git, never in `NEXT_PUBLIC_*` (except publishable keys and DSNs), never in logs.
- A production build fails if `STRIPE_SECRET_KEY` starts with `sk_test_`; development and preview never get live keys.
- One database user per environment, strong random password, least privilege.
- CI runs gitleaks; a leaked secret: rotate first, then clean the history.

## 05 Input, output, injection

- MongoDB: never pass request objects into queries; reject `$`-prefixed keys from user input; validate ObjectIds.
- Amounts, prices, fees and the commission are always computed on the server from database values.
- No `dangerouslySetInnerHTML` without sanitization (menu descriptions are plain text).
- Uploads (Vercel Blob): images only (jpeg, png, webp), max 5 MB, enforced in a short-lived client token from `POST /v1/uploads` (T-038). Product images need `menu.edit` (Manager, Owner); logo and cover need `venue.editSettings` (Owner, HQ admin with a confirmed write). The server fixes the path `venues/{venueId}/{kind}/{uuid}` (kind `product` or `venue`); `deleteBlob` (@namitiszunk/core/uploads) deletes only URLs on the Blob public host under that venue and kind, so the delete needs the same permission as the upload.
